SuryaSetu build plan

The order of work for two partners sharing one Git repo, following docs/architecture.html and docs/db-schema.html. Each phase ends with a sync point where both of you merge to main, pull, and check the app still runs. Times assume the 5-hour hackathon window.

APartner A · Backend, rules, AI

Owns api/: FastAPI, SQLite models, the rules engine, the seed script, the LLM gateway and all AI jobs.

BPartner B · Frontend, seed data, demo

Owns web/ and seed/data/: all screens, the map, voice recording, the comparison view, sample data and the demo script.

Read firstGit rules for two people

RuleWhy
main must always run. Work on short branches named feat/<area> and merge at each sync point.Either of you can demo from main at any moment.
Pull before you start and before you push: git pull --rebase origin main.Keeps history linear and surfaces conflicts early, while they are small.
Commit every 20–30 minutes with a clear message, for example feat(api): quote accept endpoint.Small commits are easy to merge and easy to undo.
Stay in your own folders. A edits api/; B edits web/ and seed/data/.Two people rarely conflict if they never edit the same file.
Shared files have one owner: api/requirements.txt, api/app/models.py, api/app/schemas.py → A. web/package.json → B. Need a change there? Ask the owner.These are the files most likely to conflict.
Whoever adds a new setting adds it to .env.example and tells the other person.Otherwise the other machine breaks on pull.
Never commit .env, *.db, uploads/, .venv/ or node_modules/. The .gitignore already blocks them.API keys stay private, and the repo stays small.
Open a pull request for each branch, even a tiny one, and let the other person glance at it before merging.Both of you know what changed without a long call.

Read firstHow data is shared through Git

The database file is not shared. Each of you rebuilds an identical local database from seed files that live in Git.

# in Git (shared)                        # on each laptop only (ignored)
api/rules/pm_surya_ghar_2024_03.yaml      api/suryasetu.db
seed/data/*.json                          uploads/
seed/photos/*.jpg                         .env

When either of you changes seed data or the models: commit, push, tell your partner. They run git pull, then python -m app.seed --reset, and both laptops hold the same data again. Rows created while testing stay local, which is what you want.

Phase 3 · 1:40 – 3:00 · 30% of the scoreCore flow: request → quote → accept

AReal endpointsfeat/core-api
  1. 3.1
    Auth: POST /auth/otp, POST /auth/verify (demo code 123456), JWT with role, a require_role() dependency.
  2. 3.2
    Uploads: POST /uploads as multipart, saved to uploads/, with a files row and sha256. This stands in locally for presigned S3 uploads.
  3. 3.3
    Requests: POST /requests runs the rules engine, saves calculations and status history, and returns the estimate with citations. Add GET /requests/mine and GET /requests/{id}.
  4. 3.4
    Vendor map: GET /requests/open?bbox= filters by lat/lng box and the vendor's service radius (haversine). Show a location rounded to about 500 m.
  5. 3.5
    Quotes: POST /requests/{id}/quotes validates, saves line items, and computes a quote_financials calculation (net cost, payback). Add GET /requests/{id}/quotes.
  6. 3.6
    Accept: POST /quotes/{id}/accept in one transaction: the quote becomes accepted, the others rejected, the request accepted. Add GET /rules/current.
BReal screensfeat/core-ui
  1. 3.7
    Login: phone, OTP, and quick buttons for the demo household and demo vendor.
  2. 3.8
    New request: click the map to pin, or "Use my location". Then photo upload, monthly units, budget, roof area. On submit, show the estimate card with each step and an ⓘ link to its rule source.
  3. 3.9
    My requests and request detail: status badge and a list of incoming quotes.
  4. 3.10
    Vendor map: pins for open requests, a side panel with request details, and the quote form (price, panel, inverter, warranty, timeline, line-item checklist).
  5. 3.11
    Compare and accept: a side-by-side table showing price, net cost after subsidy, payback, warranty and timeline. The accept button asks for confirmation on the page, then shows the accepted state.
Sync 3Merge both. On each laptop, from a fresh seed: a household posts a request, a vendor quotes it, and the household accepts. Tag it: git tag v0.1-core-flow && git push --tags.

Phase 4 · 3:00 – 4:00 · 20% of the scoreAI features

AAI jobsfeat/ai-jobs
  1. 4.1
    app/llm/gateway.py: Gemini and Groq clients, an in-memory rate limiter, a cache on input_hash in ai_jobs, Pydantic validation of output, and one retry. Jobs run with FastAPI BackgroundTasks. Add GET /jobs/{id}.
  2. 4.2
    Photo assessment: Gemini vision returns obstructions and usable fraction. Code computes usable area and maximum kW, and updates the estimate.
  3. 4.3
    Voice: POST /voice/transcribe calls Groq whisper-large-v3 with language hi, gu or en, then extracts form fields into voice_inputs.
  4. 4.4
    Quote review: code checklist for missing items, a regex plus LLM injection check, and short LLM notes.
  5. 4.5
    Scoring and recommendation: rules/scoring.py fills quote_scores. The recommend job sends only the score table to the LLM, which writes the reasons.Done when the injection quote is flagged and does not rank first.
BAI screensfeat/ai-ui
  1. 4.6
    Photo result: obstruction boxes drawn over the photo, usable area and the kW cap with its explanation.
  2. 4.7
    Voice: a mic button using MediaRecorder with a Hindi / Gujarati / English picker. The transcript prefills the form for the user to confirm.
  3. 4.8
    Comparison, upgraded: missing-item chips, a score breakdown per criterion, a warning banner on the injection quote, and a recommendation card with reasons.
  4. 4.9
    Waiting states: poll /jobs/{id} and show "AI review in progress". The page stays usable if AI fails, because every number comes from code.
Sync 4Merge both. Run the full demo once with AI on. Tag v0.2-ai.

New variable in .env.exampleCopy the line into your own .env and fill it in
Rebase conflictFix the marked files, git add them, then git rebase --continue. If stuck, git rebase --abort and ask your partner.
Gemini or Groq returns 429Wait a minute. The gateway caches results, so a retry with the same input costs nothing. Switch to your own key if you share one.
